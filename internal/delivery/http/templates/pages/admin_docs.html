Technical docs

How this app is put together and what actually runs for each major action — admin-only, since it names internal handlers, services, and tables rather than describing how to use the product (that's Help). For the reasoning behind a design choice rather than the mechanics of it, see CLAUDE.md in the repository.

Layering

Dependencies point one way only. A handler calls a service; a service calls a repository interface declared in domain; SQL never leaves repository/postgres.

delivery/http (routing, handlers, templates) → service (business rules) → domain (entities, ports) ← repository/postgres (SQL, implements the ports)

Every request, before it reaches a handler

Server.Handler() wraps the mux in a fixed order — each stage can short-circuit the ones after it:

  1. recoverer — catches a panic, logs it, returns a 500 instead of crashing the process.
  2. requestLogger — one structured log line per request (method, path, status, duration).
  3. securityHeaders — CSP, X-Frame-Options, nosniff on every response.
  4. csrfProtect — double-submit cookie check on every mutating method (POST/PUT/PATCH/DELETE), including the login form itself.
  5. loadSession — reads the session cookie, calls AuthService.ValidateSession, and puts the resulting *domain.User (or nil) on the request context.
  6. the mux, then whichever of requireAuth / requireWrite / requireAdmin wraps that specific route.

requireWrite and requireAdmin both call requireAuth first, then check user.Role.CanWrite() / CanManageUsers() — a role check always happens server-side, never only in the template.

Request flows

Sign in with MFA

  1. 1. POST /login → handleLoginSubmit → AuthService.Login checks the bcrypt hash via authcrypto, records a login_failed audit entry on a bad password, and on success returns a short-lived signed "password verified" token — no session cookie yet.
  2. 2. GET /login/mfa → handleMFAChallengePage — plain form render, the pending token round-trips as a hidden field.
  3. 3. POST /login/mfa → handleMFAChallengeSubmit → AuthService.VerifyMFA checks the TOTP code (or a one-time recovery code via tryRecoveryCode), then createSession mints a random 32-byte token, SHA-256-hashes it before UserRepository stores it, and the raw token becomes the session cookie.

Generate a CSR

POST /certificates/generate (requireWrite) → handleCertificateGenerate parses the form (subject fields, SANs, key spec, requested EKU) → CertificateService.CreateCSR calls certutil.GenerateKey then certutil.CreateCSR (which attaches the EKU extension-request), encrypts the key via the secret.Sealer if configured, and CertificateRepository.Create inserts one row with Status = pending.

Import a CSR + key generated elsewhere

POST /certificates/import-csr (requireWrite) → handleCertificateImportCSR → CertificateService.ImportCSR parses the pasted CSR with certutil.ParseCSRPEM, pulls subject/SANs/requested-EKU straight off it, confirms the pasted key matches via certutil.MatchesCSRKey, then stores it the same way as Generate — same Origin = generated, since what differs is which machine ran the keygen, not the lifecycle.

Upload a certificate (PEM or PKCS#12)

POST /certificates/import → handleCertificateImport → CertificateService.Import for a pasted PEM triplet; POST /certificates/import-pfx → handleCertificateImportPFX → ImportPFX (single file) or BulkImportPFX (multipart, several files against one shared password, one BulkImportResult per file) — both decode via certutil.DecodePKCS12. Either path lands with Origin = uploaded and Status = issued immediately (no pending stage), and checks CertificateRepository.FindSharingFingerprint to flag a duplicate already on file.

Attach the CA's response to a pending CSR

POST /certificates/{id}/certificate (requireWrite) → handleCertificateAttach → CertificateService.AttachCertificate splits the pasted PEM into leaf + chain via certutil.ParseCertificatesPEM, checks the leaf's public key matches the stored private key (certutil.MatchesKey), then applyIssuedCert copies subject/issuer/signature/EKU straight off the parsed leaf onto the record — the issued certificate becomes ground truth for EKU from this point on, overwriting whatever was requested at CSR time.

Issue a pending CSR (self-sign, an existing Root CA, or a brand-new one)

POST /certificates/{id}/issue (requireWrite) → handleCertificateIssue — one endpoint for the pending-certificate detail page's single "Sign with" dropdown (v1.9; previously two separate forms/endpoints side by side). sign_action selects the path: empty or "self" calls CertificateService.SelfSign, which re-parses the stored CSR and key, calls certutil.SelfSign (issuer == subject, honours the record's stored EKU), then the same applyIssuedCert path as Attach; an existing Root CA's UUID calls CertificateService.SignWithRootCA the same way; "new" calls CertificateService.GenerateRootCAAndSign, which mints a brand-new Root CA from the request's CA-subject/key fields (the same certutil.GenerateRootCA the Issuers page's "Generate a Root CA" uses) and immediately signs with it — the new CA is left in place afterward even if signing somehow then fails, since it's still a perfectly valid CA available from the Issuers page.

Edit a certificate's chain

POST /certificates/{id}/chain (requireAdmin) → handleCertificateChainUpdate → CertificateService.UpdateChain parses the pasted chain with certutil.ParseCertificatesPEM (a hard failure here — unparseable input — is rejected outright), then certutil.ValidateChain checks that each intermediate actually signed the one before it, is marked as a CA, and isn't expired. A failed *validation* still saves — the admin sees exactly which link is broken instead of being locked out — only a parse failure blocks the save.

Download / export

GET /certificates/{id}/download (requireAuth, format-gated inside the handler — admin for anything with key material, editor may still take a bare .csr) → handleCertificateDownload → CertificateService.Export → certutil.Export, which switches on format to produce PEM/DER/PKCS#7/PKCS#12/ZIP. A key-bearing download (.key, .pfx, .zip) is separately audited as private_key_downloaded.

Editing the Help page

POST /help/edit (requireAdmin) → handleHelpEditSubmit → SiteContentService.SetHelpContent → SiteContentRepository.SetSiteContent upserts a row in site_content keyed "help". GET /help reads it back through HelpContent, falling back to the compiled-in service.DefaultHelpContent when no row exists yet, and renders it unescaped (template.HTML) — the one place in the app that does, which is why writing it is admin-only.

Switching light/dark

POST /theme (public, no auth) → handleThemeToggle flips a plain theme cookie and redirects back to the page that was toggled from. There is no client-side theme script at all: newView reads the cookie via themeFromRequest on every request and stamps <html data-theme="..."> server-side, so there's nothing to flash-of-wrong-theme on load. The palette itself is CSS custom properties in web/input.css (--color-*, overridden under [data-theme="light"]), consumed through semantic Tailwind colors (surface, card, line, ink/ink-1..6, hue-*) defined in tailwind.config.js — templates use these instead of raw slate/white shades so both themes update from one place.
